# Known issues

One line each. Not exhaustive — just things flagged during work and not yet resolved or verified.

- ~~Header text is clipped by the settings gear icon on the game screen~~ — **fixed and confirmed in Phase 2**: the header was rebuilt as a real flex row (`GameHeader.tsx`) instead of an absolutely-positioned icon over full-width text; verified on a real device with no overlap at "Chapter 1 · 2" and longer titles.
- Retry rate isn't instrumented in the generator: `gen.ts` only records overall success/failure per level, not how many of the up-to-200 attempts inside `generateLevel` were consumed per success.
- No property-based testing library is installed; the section 7 validation "tests" in `generator.test.ts` are a fixed-seed loop of 20 samples, not real property tests with shrinking.
- Section 14's "downloaded level pools go in a folder excluded from Android auto-backup" isn't implemented: Phase 2 still bundles fixed level data in the app, there's no pool-download flow yet, so there's no downloaded-pools folder to exclude. Revisit when pool downloading exists.
- ~~`GameScreen` picks a fresh level via `pickCurrentLevel()` on every mount~~ — **fixed and confirmed**: `currentLevel` (plus wheel arrangement and hinted cells) now lives in `AppState`, which outlives a `GameScreen` remount; `GameScreen`'s effect only picks a new level when `currentLevel` is `null`. `startNewLevelRun()` explicitly clears it on level completion — that's the only path that should trigger a re-pick. A first attempt at this fix used a `GameScreen`-local `useRef` to track "already picked," which looked right in code review but didn't actually work: a ref is exactly as fresh on remount as `useState` is, since it only survives re-renders of the *same* mounted instance, not an unmount+remount. Confirmed via real logcat output (`VERIFY GameScreen effect: currentLevel=<id>` unchanged across a Settings-and-back navigation, `picking a new level` only firing on genuine completion) and matching on-screen grid/wheel/progress before and after.
- The first-run tutorial (`TutorialScreen.tsx`) is a static 4-step text walkthrough, not the "guided levels" Plan.md section 12 describes (actual swiping/shuffling/hints inside a real level). Scoped down for the Phase 2 gate; revisit for a truly interactive tutorial.
- Sound effects (`packages/tools/src/gen-sounds.ts`) are synthesized placeholder sine tones, not real sound design.
- The word-language picker only ever lists English, since only one word pack (`en`) exists — untested with more than one language.
- Metro (the dev JS bundler) can silently hang: it keeps accepting TCP connections on :8081 but stops responding to any request, including a plain `/status` check. From the phone this looks exactly like the app crashed — a persistently blank screen with zero JS logs (no "Running main", nothing) even though the native side booted fine and the dev-client shows as connected. Before assuming the app itself is broken, check Metro's actual responsiveness directly (`curl http://localhost:8081/status` — a hung instance times out with 0 bytes even though `netstat` shows it LISTENING) rather than just checking that a process exists on the port. Fix is to kill that Metro process and start a fresh one; this cost significant debugging time before the actual cause was found by curling it directly instead of trusting the device-side symptoms.
- Metro's own bundle cache can also serve stale JS after a restart without the app or Metro process itself looking broken: after edits to `AppState.tsx`/`GameScreen.tsx`, a `force-stop` + relaunch loaded a bundle where the new code silently didn't run (verified by a total absence of a diagnostic log that should have fired on every mount), while Metro's dev log showed only a `"total":1` incremental bundle rather than a full rebuild. `expo start --dev-client --clear` (clearing Metro's cache explicitly) resolved it. If a JS change doesn't seem to be taking effect despite a full app restart, don't assume the edit is wrong — check whether Metro actually rebundled from scratch.
