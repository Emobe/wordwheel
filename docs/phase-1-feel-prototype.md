# Phase 1: Feel Prototype

Expo development build, Android first. Prove the core interaction loop feels good and the Phase 0 word data works on-device, before any monetisation, art, or content investment.

## Gate (PLAN.md section 12)

- Runs on an Android emulator and at least one real phone, ideally a low-end one.
- Swipe wheel, grid fill, bonus words, shuffle, hints all work, with placeholder flat-colour art only.
- Smooth swipe (steady frame rate during the pan gesture).
- Acceptable pack load time and memory on device.

## Scope

Swipe-to-spell wheel, crossword grid fill, bonus-word tracking, a shuffle button, and unlimited free hints (no ad gating — that's Phase 2). One bundled level pack, generated by the Phase 0 CLI.

## Out of scope

- Any art beyond flat colours/system fonts. No Skia, no backgrounds — that's the Phase 3 visual design pass (PLAN.md section 8).
- Ads, purchases, consent flow, RevenueCat, AdMob — Phase 2.
- Saves/progression across sessions, sound, haptics — Phase 3.
- Real accepted-word validation for arbitrary player typing beyond swipe (Phase 1 only needs swipe-to-spell against the wheel's own tiles).

## Decisions needing sign-off before implementation starts

These fall under CLAUDE.md's "ask first" list:

1. **Native dependencies to install** (adding/upgrading a native dependency needs sign-off): `expo-dev-client` (required — Expo Go can't do ads/purchases later and CLAUDE.md already rules it out), `react-native-gesture-handler` and `react-native-reanimated` (swipe wheel, UI-thread animation), `react-native-svg` (draw the swipe trail without pulling in Skia early — Skia is scoped to the Phase 3 visual pass). No ad/purchase SDKs this phase.
2. **Build method**: a local Android build (Android Studio + SDK, `npx expo run:android`, no cloud cost) versus an EAS cloud dev-client build (costs money, needs its own go-ahead per "starting a cloud build (EAS) or anything that costs money"). Recommend local first; fall back to EAS only if local toolchain isn't available.
3. **App identifier / working title**: PLAN.md still has the title as TBD and explicitly bans anything Wordscapes-lookalike. Need a placeholder Android application ID (e.g. reverse-domain under a name you own) to scaffold `app.json` — doesn't need to be final, just not a name that collides with the reference game.
4. **On-device accepted-word format**: spike list item — ship the accepted-word set as a bundled newline-delimited text asset, parsed into `packages/core`'s existing `Trie` at app startup. Simplest option that reuses Phase 0 code as-is. If the on-device load-time/memory gate fails, fall back to a packed/binary trie format — that's a real risk, not a formality, and is called out as its own milestone below so it can fail visibly instead of being assumed away.

## Granular task breakdown

**M1 — Scaffold the Expo app**
- Scaffold `apps/mobile` (TypeScript template), add `apps/*` to the root `package.json` workspaces glob.
- `app.json`: portrait-only orientation, placeholder application ID, dev-client enabled.
- Record the scaffolded Expo SDK version and its default `targetSdkVersion` in this doc (spike list item — must be API 36 per PLAN.md section 11, or bumped if not).
- Install `expo-dev-client`.

**M2 — Verify Metro resolves `packages/core`** (spike list item)
- Configure `metro.config.js` for the Bun workspace monorepo (watchFolders, nodeModulesPaths).
- Add a throwaway screen that imports something from `@wordscapes/core` (e.g. `Rng`) and renders its output, to prove bundling and Hermes execution both work.
- Record pass/fail here before building anything real on top.

**M3 — Minimal `PlatformServices` interface**
- Define the interface in `packages/core` (per the mobile rule: all native calls go through it, `core` never touches native code directly).
- Phase 1 only needs a clock and (maybe) storage for the bundled pack; stub ads/purchases as explicit "not available yet" so the shape exists without pulling in real SDKs early.
- Implement the real version in `apps/mobile`; a fake/in-memory version for any core tests that need it.

**M4 — Load the accepted-word set on-device**
- Export `data/build/packs/en/accepted.txt` (or a trimmed subset for a faster first pass) as a bundled asset in `apps/mobile`.
- Parse it into `packages/core`'s `Trie` at startup; time it and log memory.
- This directly resolves the spike list's "accepted-word set load time and memory on device" item — record the numbers here, not just "it worked."

**M5 — Load one bundled level pack**
- Run `bun run gen` to produce a small level set, copy a handful into `apps/mobile` as a bundled JSON asset (real device-download-on-demand per PLAN.md section 6 is later; Phase 1 just needs something to render).
- Screen/state to hold "current level."

**M6 — Wheel UI: swipe-to-spell**
- Circular layout of the level's wheel tiles, flat-colour circles + system font text.
- `react-native-gesture-handler` pan gesture across letters; `react-native-reanimated` for on-UI-thread trail/highlight updates; `react-native-svg` to draw the trail path.
- On gesture release, build the candidate word from the swiped tile order and check it against the accepted-word `Trie` from M4.
- Note: this in-app shuffle/swipe logic is UI interaction, not level *generation* — CLAUDE.md's "never use `Math.random`, deterministic from a seed" rule is scoped to `packages/core` generation, not `apps/mobile` UI cosmetics. Worth stating explicitly so it's not misread later.

**M7 — Grid fill**
- Render the crossword grid from `level.grid.words` (blank vs. filled cell states, flat colours).
- When a swiped word matches a grid word, fill those cells.

**M8 — Bonus words**
- Call `packages/core`'s `bonusWords()` once the level and its accepted-word trie are loaded.
- Track found/total bonus words as swiped words match a bonus word; simple counter UI, no list view needed yet.

**M9 — Shuffle button**
- Re-render the wheel with tiles in a new order on tap. Purely cosmetic client-side randomness (fine to use `Math.random` here per the M6 note above).

**M10 — Hints**
- Unlimited, free hint action for Phase 1: reveal the first letter of one unsolved grid word. No ad gating (Phase 2), just wire the affordance through the M3 `PlatformServices` stub so the real ad-gated version slots in later without a UI rewrite.

**M11 — Device testing pass**
- Run on an Android emulator, then at least one real phone (ideally low-end, per the gate).
- Check: swipe frame rate under `react-native-reanimated`/`react-native-gesture-handler` on that low-end device (spike list item), pack load time (M4's numbers, now on real hardware not just emulator), memory footprint.
- Record results in this doc; this is the actual phase gate, not "it compiled."

## Risks worth flagging now

- The accepted-word `Trie` (M4) is currently an in-memory JS object graph built from Phase 0's `packages/core` code, sized for a Bun process — it has never been measured on Hermes. If load time/memory fails the gate, the fallback (packed binary trie or sorted-array binary search) is a real follow-up task, not a footnote.
- Reanimated on the New Architecture has known regressions per the spike list — M11 is where that gets confirmed or contradicted, not assumed fine because it works in the emulator.
